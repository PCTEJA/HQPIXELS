# 100,000 Concurrent Viewers — Load Test Plan

**Document type:** Plan (not executable test)  
**Status:** Theoretical — requires dedicated infrastructure  
**Author:** Load Test Suite (Task F)  
**Date:** 2026-08-25

---

## 1. Overview

This document outlines the requirements, methodology, and expected outcomes for testing
HQPixels under 100,000 concurrent viewer load. This test is NOT executed as part of the
standard test suite due to infrastructure requirements and costs.

### 1.1 Goals

1. Validate edge caching holds under viral traffic conditions
2. Identify breaking points and graceful degradation patterns
3. Establish scaling guidance for infrastructure decisions
4. Document failsafe behaviors (circuit breakers, rate limits)

### 1.2 Non-Goals

- Testing payment flows under load (Stripe sandbox limits apply)
- Testing write operations at 100k scale (database would be bottleneck)
- Achieving 100k sustained for hours (cost-prohibitive)

## 3. Test Scenarios

### 3.1 Scenario A: Gradual Ramp (Primary)

```
VUs: 0 → 10k → 50k → 100k → hold → ramp down
Duration: 30 minutes total

Timeline:
  0:00 - 5:00   Ramp 0 → 10,000 VUs
  5:00 - 10:00  Ramp 10,000 → 50,000 VUs
 10:00 - 15:00  Ramp 50,000 → 100,000 VUs
 15:00 - 25:00  Sustain 100,000 VUs
 25:00 - 30:00  Ramp down to 0
```

**Traffic distribution:**
- 85% GET /api/wall/manifest
- 10% GET /api/public/stats
- 5% GET /go/:id (redirect sampling)

### 3.2 Scenario B: Viral Spike

Simulates social media referral traffic (sudden spike):

```
VUs: 0 → 100k in 2 minutes → hold 5 minutes → crash
Duration: 10 minutes

Purpose: Test circuit breaker and rate limiter behavior
Expected outcome: Graceful degradation, not cascading failure
```

### 3.3 Scenario C: Geographic Distribution

```
Regions: US-East, US-West, EU-West, EU-Central, APAC
Distribution: 30%, 20%, 25%, 15%, 10%
Total VUs: 100,000
Duration: 20 minutes
```

## 4. Success Criteria

### 4.1 Performance Budgets (100k load)

| Metric | Target | Acceptable | Failure |
|--------|--------|------------|---------|
| p50 latency | <100ms | <200ms | >500ms |
| p95 latency | <300ms | <500ms | >1000ms |
| p99 latency | <500ms | <1000ms | >2000ms |
| Error rate | <0.1% | <1% | >5% |
| Cache hit rate | >95% | >90% | <80% |
| Origin requests/sec | <500 | <1000 | >2000 |

### 4.2 Behavioral Requirements

- [ ] No complete outages (always some capacity)
- [ ] Rate limiter engages before system saturation
- [ ] Circuit breaker trips on database overload
- [ ] Cached content remains available if origin fails
- [ ] Error pages are informative (not stack traces)
- [ ] Recovery within 5 minutes of load reduction

## 6. Expected Outcomes

### 6.1 Optimistic (Infrastructure Sufficient)

- System handles 100k with p95 <500ms
- Cache hit rate >95%
- Origin sees <200 requests/second
- Zero data corruption or partial states
- Graceful degradation if limits hit

### 6.2 Realistic

Based on architectural analysis:

| Stage | VUs | Expected Behavior |
|-------|-----|-------------------|
| 0-10k | 10,000 | Full performance, all budgets met |
| 10k-50k | 50,000 | Slight latency increase, rate limits begin |
| 50k-75k | 75,000 | Rate limiter active, some 429 responses |
| 75k-100k | 100,000 | Degraded mode, stale cache served |

**Bottleneck prediction:** Database connections (not Worker or CDN)

### 6.3 Failure Modes

| Failure | Symptom | Mitigation |
|---------|---------|------------|
| Database saturation | 500 errors spike | Circuit breaker, stale cache |
| Worker CPU exceeded | 502 Gateway Timeout | Scale to Paid tier |
| Cache stampede | Origin overwhelmed | Lock/queue pattern |
| Rate limiter cascade | Legitimate users blocked | Adjust limits |
